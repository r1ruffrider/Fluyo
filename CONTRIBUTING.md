# Contributing to Fluyo

## Purpose

This document defines how contributors should work within the Fluyo repository. It provides a consistent onboarding and delivery process for human developers and AI coding assistants across all development efforts.

All contributors—human or AI—must review and follow the repository's documented standards before proposing or making architectural or implementation changes. Product requirements, architecture, and accepted Architecture Decision Records (ADRs) take priority over personal preferences and tool defaults.

---

## Read These Documents First

Before beginning work, review the repository documentation in this order:

1. [`docs/PLATFORM_STANDARDS.md`](docs/PLATFORM_STANDARDS.md)
2. [`docs/BUSINESS_PLAN.md`](docs/BUSINESS_PLAN.md)
3. [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md)
4. `docs/ROADMAP.md` (when available)
5. `docs/PRD.md` (when available)
6. `docs/API.md` (when available)
7. `docs/DATABASE.md` (when available)

Review any relevant ADRs and security documentation when the proposed change affects their scope. If documentation conflicts, `docs/PLATFORM_STANDARDS.md` takes precedence unless an accepted ADR explicitly approves a scoped exception.

## AI Development Policy

Fluyo supports development with multiple AI coding assistants. Examples include:

- ChatGPT
- ChatGPT Codex
- Claude
- GitHub Copilot
- Cursor
- Windsurf
- Gemini
- Future AI assistants

Repository decisions must never depend on a specific AI tool. Documentation, prompts, workflows, and architecture must remain usable by contributors regardless of which approved assistant they use.

Implementation must follow documented requirements and architecture rather than assumptions generated by an AI assistant. AI-generated contributions receive the same review, testing, security, and documentation requirements as human-authored contributions.

## Development Workflow

Use the following workflow for every change:

1. Review the existing documentation and relevant ADRs.
2. Understand the requested feature, its acceptance criteria, and the systems it affects.
3. Inspect existing code and patterns to avoid duplicate functionality or competing abstractions.
4. Make focused, incremental changes that address one clear objective.
5. Update documentation whenever behavior, architecture, data, APIs, security, billing, or operations change.
6. Verify formatting and linting with the repository's configured tools.
7. Run applicable unit, integration, and end-to-end tests.
8. Submit changes with a meaningful Conventional Commit message and a clear pull-request description.

Do not broaden the scope of a task without documenting the reason. Preserve unrelated work already present in the repository.

## Coding Standards

Follow [`docs/PLATFORM_STANDARDS.md`](docs/PLATFORM_STANDARDS.md). At minimum:

- Enable and preserve TypeScript strict mode.
- Follow the shared ESLint configuration.
- Format supported files with Prettier.
- Organize application code by feature or domain.
- Prefer small, reusable components and testable services.
- Use clear, consistent names that communicate intent.
- Keep business logic out of presentation components and thin transport layers.
- Validate data at trust boundaries.
- Avoid unnecessary dependencies; prefer existing platform capabilities and approved shared packages.
- Avoid provider-specific behavior outside dedicated integration adapters.

New dependencies require a clear need, maintenance assessment, security review, and confirmation that an existing dependency does not already solve the problem.

## Documentation Requirements

Documentation is part of feature completion. Update the appropriate documents whenever a significant change affects:

- architecture or system boundaries;
- database schemas, migrations, ownership, retention, or recovery;
- API contracts, authentication, errors, pagination, or versioning;
- security controls, permissions, secrets, or threat assumptions;
- billing, subscriptions, webhooks, coupons, or entitlements;
- deployment, infrastructure, configuration, or operations;
- product requirements, behavior, or roadmap status.

Do not leave important decisions only in code, a pull request, or an AI conversation. Clearly distinguish implemented behavior from future plans.

## Git Workflow

- The `main` branch is protected. Do not push unreviewed production changes directly to it.
- Create a short-lived feature branch for each focused change.
- Submit changes through a pull request.
- Obtain the required code review and passing CI checks before merge.
- Use Conventional Commits.
- Keep commits focused and avoid mixing unrelated refactors with feature work.

Common commit types include:

```text
feat: add a user-facing capability
fix: correct faulty behavior
docs: update documentation only
refactor: restructure code without changing behavior
test: add or update tests
chore: perform maintenance work
```

Use an imperative, concise subject and add a commit body when the rationale or migration impact is not obvious.

## Pull Request Checklist

Complete this checklist before requesting review:

- [ ] I reviewed the relevant repository documentation.
- [ ] I followed `docs/PLATFORM_STANDARDS.md` and applicable ADRs.
- [ ] I added or updated tests where applicable and ran the relevant test suites.
- [ ] I updated documentation for affected behavior, architecture, data, APIs, security, billing, or operations.
- [ ] I confirmed that no secrets, credentials, tokens, certificates, or private data are committed.
- [ ] I did not add unnecessary dependencies.
- [ ] I preserved compatibility with Forge's billing architecture and shared entitlement model.
- [ ] I reviewed the security and privacy implications of the change.

If an item does not apply, explain why in the pull-request description rather than silently ignoring it.

## Billing Requirements

Fluyo must remain compatible with Forge's billing architecture and shared billing data model. Follow [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) and `docs/PLATFORM_STANDARDS.md`.

Do not introduce:

- a different payment provider;
- a different subscription lifecycle or model;
- a separate entitlement system;
- a custom checkout or card-entry flow;
- a custom coupon or discount engine; or
- feature authorization based directly on client claims, Stripe Price IDs, or redirect parameters.

Web billing must remain aligned with Forge's Stripe architecture: Stripe Checkout, Stripe Customer Portal, signed and idempotent Stripe webhooks, monthly and annual subscriptions, Stripe coupons and promotion codes, and provider-neutral entitlements.

RevenueCat remains reserved for future native mobile applications. When introduced, it must map native purchases into the same identity and entitlement model rather than create a parallel authorization system.

---

## Security Requirements

Never commit:

- API keys;
- access or refresh tokens;
- webhook or application secrets;
- private certificates or private keys;
- database credentials;
- service-account credentials; or
- production customer data.

Use environment variables or an approved secret manager for configuration and secrets. Commit only documented example variable names with non-sensitive placeholder values.

Privileged credentials must remain server-side. Validate untrusted input, enforce authorization on the server, use HTTPS outside local development, apply least privilege, and avoid exposing internal errors or provider payloads to clients. If a secret may have been exposed, stop using it, rotate it promptly, and follow the documented incident process.

## AI Contributor Guidelines

AI assistants should:

- read the required documentation before modifying code;
- inspect existing patterns and preserve architectural consistency;
- avoid speculative implementations that are not supported by requirements;
- ask for clarification when requirements or documents materially conflict;
- explain significant architectural changes and their tradeoffs;
- avoid rewriting or reformatting unrelated code;
- keep each change and commit focused on a single objective;
- preserve user-authored and unrelated in-progress changes;
- validate generated code with the same formatting, linting, testing, and security checks as human-authored code; and
- state assumptions and distinguish verified behavior from planned behavior.

AI assistants must not select architecture, dependencies, providers, or data models merely because they are defaults of a particular tool.

## Architecture Decision Records

If a significant architectural decision changes:

1. Create a new ADR under `docs/adr/` using the naming convention defined in `docs/PLATFORM_STANDARDS.md`.
2. Explain the context, constraints, and reason for the decision.
3. List the alternatives considered and why they were not selected.
4. Document security, data, operational, cost, and compatibility consequences.
5. Reference all impacted documentation and related or superseded ADRs.

Do not rewrite an accepted ADR to hide a changed decision. Create a new ADR that supersedes it and preserves the decision history.

---

## Repository Philosophy

Fluyo is intended to become a long-term production platform. Quality, maintainability, documentation, security, and consistency take priority over rapid feature development.

Contributors should choose clear, durable solutions; reduce unnecessary complexity; and leave the repository in a better state than they found it.
